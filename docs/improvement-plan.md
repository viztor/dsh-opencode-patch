# Improvement plan

## Context

The result of an architecture audit of the tree at 1.4.1, and the order in which to act on it. It rests on:

- six audits: routing, catalog, credentials, config/UI, tests/CI/docs, and the stream path;
- an adversarial review of the plan itself, then a nine-lens review (five reviewers, four investigators) in which two independent skeptics checked every finding: 78 of 82 were upheld and are folded in here;
- the host's own source and data (`deepseek-ai/deepseek-harness`, and the pi 1.1.0 catalog its `0.2.1` rc tags pinned; the `0.2.2` tags of both channels declare pi `^1.3.0`, whose floor is what the desktop app ships, D14''). File references into the host are relative to that repository's `packages/`.

**Restacked onto 1.8.0 (November 2026).** The stack was cut from 1.4.1. Since then `main` moved to 1.8.0 and followed the harness onto its **alpha** track (the `0.2.2-alpha.2` cluster, cordis `4.0.6-alpha.1`, pi `1.4.0` exact), and it landed several things the plan had scheduled: the plane-aware price, free flag and refusal (#133), a working retired alias (#135), the synthetic catalogue fixtures (#138), the language-pair gate and the live-run verdicts (#140), and the scripts' pure halves (#143, #144). Since 1.9.1 the stack lands by rebase, not by merge: the owner rebased P0 to P-H onto `main` as one commit each (#105, #106, #155, #108, #109, #110, #112), and each open phase is rebased onto its rebased parent as its own change, followed by the adaptation commits the rebase needs, never re-adding or reverting what `main` already has. What changed in the decisions is under "Owner decisions" (D14'', D22'', D16 and D17 as rewritten by D26, D23, D24, D25, D26), what changed per phase is under "Restack adjustments", and what two community plugins built on the same host taught is under "Lessons from opencode2dsh". A new phase, P-R3, follows P-T3.

**Outcome:** a plugin that only uses host extension points the host supports; one source of truth per decision; a suite that pins behaviour before it moves; and the owner's product rules below.

**Each phase is one pull request**, and it updates this document: its row below moves to "merged", and its section is trimmed to what is left. A finding that does not survive its phase's first failing test is struck from here rather than forced.

The 1.x Settings discovery wrapper (`decorateModelDiscovery`) leaves pi-ai's Fetch answer for a stepped-aside plane untouched, and P3's discovery complement must exclude stepped-aside planes the same way. A live edit moves a plane either way at once, with no restart: one that drops the marker hands the plane to the plugin at the commit's reconcile, and one that adds it releases the plugin's registration of that plane inside the commit run itself (on the row that registration was built from, even when, beside a second pi-ai row, that row is no longer the one the claim would serve once it takes nothing), before pi-ai registers the routes of the config it is applying, which would otherwise be refused as a duplicate and leave the route with no adapter. A live edit of an `isolate` alone (pi-ai's row's, the plugin's own row's, or a group's around either), which the loader applies by swapping the realm map in place with no config run, no restart and no registry change, moves the planes too, with one restart: the reconcile scheduled on every row's `loader/partial-dispose` releases a plane the claim no longer takes and restarts pi-ai once it settles, so pi-ai re-resolves and registers it, and restarts a pi-ai that holds a plane the claim now takes, so it re-resolves through the listener; each restart is asked once per need, never again for a row whose shape did not change. The purge (D8) never rewrites another plugin's entry either: it skips a provider row carrying the marker and every plane entry of a row in a realm its own context does not resolve (the process-wide realm, since it is a root service), and leaves a reference to a route only such entries declare; with no plane entry of the user's own it refuses, writing nothing. |

## Routing: the problem, the measured facts, the design

**The problem, in the owner's words.** A provider defines one backend. Supporting every protocol and the newer catalog meant un-registering the original `opencode`/`opencode-go` provider and registering the plugin's own. Deleting another plugin's registration is unsupported, so the plugin mounted extra routes per protocol instead, merged their models back into the user's provider, and redirected dispatch. This section shows that the host **does** allow the original intent, through supported paths (F11–F13): keep pi-ai from claiming the two ids, and register the plugin's provider under them. A spike on the real host confirmed it (run S0).

**Facts from the host's own code and data.** F1–F5 and F10 are measured: the data files were counted and the resolver read. F6–F9 and F11–F13 are read from the code, and run S0 exercised F11–F13 end to end. P-T1's real-host harness pins the ones the host can answer in-process: P-T1b pins F1, F2, F4, F5, F8, F10–F16, F18 and F20 by number (F3 through its F4 consequence, F7 through F13's register and DUPLICATE halves); F6 (dispatch through a non-pi adapter) and F19's auth half (constructing a `PiAiAdapter`) are first exercised by P-R1, F6 through its mock gateway and the real `LlmRuntime`; F19's export half is pinned in `host-shapes` (`recordKeyFor`); F17 is honoured, not pinned — tier B fixes the apply order and the binary e2e infers it; F9 is a fact about opencode's own client, outside this host. A fact that fails where it is pinned sends the design back to this section. Where the two cordis cores differ (F8, F12, F14, F16, F17, F20), the row states both: first the NEW core (cordis `4.0.6-alpha.2` and `4.1.0`, one `src` tree, which both channel records run), then the OLD core (cordis `4.0.5`, `4.0.6-alpha.1`), which no supported channel ships and which the stand-ins of `test/support/config-shape.ts` hold. ### The design: the plugin owns the plane routes (D13)

#### `src/host/route-claim.ts`: pi-ai never claims the planes

_As built, on both cores (P-R1, from F8, F12, F14, F16 and F17's per-core text). The first design prepended the listener and ran a nested waterfall, which only the OLD core (cordis `4.0.5`, `4.0.6-alpha.1`) dispatches the way it assumed; on the NEW core (cordis `4.0.6-alpha.2` and `4.1.0`, one `src` tree, which both channel records run) that listener saw no fiber and pi-ai kept both planes, the binary e2e's `[KNOWN_DEFECT]` row until the claim spoke both shapes. One appended listener serves both, told apart by the call and the fiber's own fields (`src/utils/config-run.ts`), never by a version, so no OLD-only prepend path is kept. The OLD shape was measured once on a published binary, `0.2.1-rc.5` (cordis `4.0.5`), on 2026-11-12, with the binary e2e's record check lifted locally; no committed cell runs the OLD core, and the standing OLD-shape coverage is the stand-in fibers of `test/route-claim.test.ts` (`piFiber`, `oldRun`) and `test/config-run.test.ts`._

- **Where the listener lives.** The plugin root declares `inject: []`; today it is `["llm"]`. The `internal/config` listener (appended, and re-appended whenever pi-ai reaches `internal/status` ACTIVE, since pi-ai appends its own checking listener at every activation) and the stream and fetch hooks live on the root, and everything that needs `llm` runs inside `ctx.inject(["llm"], scope => …)`.
  - The run's fiber is `this` on the OLD shape (`function (this: Fiber, raw, next)`) and the first argument on the NEW one (`(fiber, next)`, `this` null), recognised structurally (`fiber.ctx.fiber === fiber`); `next` is the last argument on both, called exactly once (the NEW core throws on a second call), and what it answers is the run's raw candidate, because the listener is innermost.
  - pi-ai is identified by `fiber.runtime?.name === "llm-pi-ai"`, never by `fiber.name`, which pi-ai's inject children inherit.
  - Its fibers are found through `ctx.registry` runtimes.
- **What the listener does.** It is a pure filter and never mutates its input:
  1. It strips the plane keys it TAKES from a fresh copy of what `next()` answered, and returns the copy, so every listener outer to it (pi-ai's save check included) sees no plane of the plugin's. A plane entry another plugin owns (D27: pi-ai's row resolving `credentials` in a realm the plugin's context does not, or an entry carrying the `x-opencode-plugin` header) is not taken: it stays in the copy, pi-ai validates, registers and serves it, and nothing below counts it. "Taken" is read from the run's own candidate, so an edit that adds or drops the marker is judged as the edit has it; on a commit, a plane the plugin has registered and the candidate no longer lets it take is released through the live handle before the run returns, so pi-ai's registration of it meets no duplicate. That release is decided for the row the registration was built from, before the served-row check: beside a second pi-ai row, a served row whose candidate takes nothing is no longer the row the claim would serve, yet the plugin still holds its planes.
  2. On a commit, it schedules `reconcile` with `queueMicrotask`. A commit is the fiber's own raw config (`rawConfigOf`: `rawConfig`, else `_config`), or the loader's stored row config (`entry.options.config`, the NEW core's `update()` resolving before it stores), or any run while the fiber is not ACTIVE (an activation: on the NEW core a FAILED fiber recovers only through `update()`, F17).
  3. On an editor candidate, it strictly validates the taken plane entries that changed. A malformed save is rejected in pi-ai's message style; a stepped-aside entry meets pi-ai's own check.

  It never throws on a commit run, because a throw there would fail pi-ai's fiber and every route it holds.

- **What `reconcile` does.** It reads the committed plane entries the claim takes from pi-ai's raw config (`rawConfigOf(piFiber).providers`), memoized by object identity plus a JSON comparison; on the way it logs, once per entry, each plane it leaves to pi-ai and why (D27). Then:
  1. It interpolates `{__jsExpr}` nodes with the loader's exported `interpolate` (F16). Without a loader, a node left over becomes a per-model `INVALID_CONFIG`.
  2. It normalizes the entries with pi-ai's exported `Config`, and builds the profiles.
  3. It reconciles the route set:
     - with no handle and at least one plane, it calls `registerAdapter(routes)`;
     - with a handle whose route set, `displayName` or `retryPolicy` changed, it calls `handle.replace(routes)`. `replace([])` is legal; `registerAdapter([])` is not.

  Only the planes the user declared, and the claim takes, are registered. "pi-ai still holds a plane" (the early return that waits for a restart), the served row's choice, the mount's and a handover's restart, the teardown's handback and its "did not take back" check all read the taken planes only, so a stepped-aside entry never restarts pi-ai, never holds the reconcile back, and is never handed back. The one exception is a live change of an `isolate` alone (pi-ai's row's, the plugin's own row's or an enclosing group's; D27), which no config run follows: a plane pi-ai resolved stripped and now keeps is released, then pi-ai is restarted once it settles; a plane pi-ai resolved holding and the claim now takes restarts pi-ai instead of holding the reconcile back. Each such restart is recorded by what it was for and asked once. `reconcile` also runs on a global `llm/adapters-updated`, and on every row's `loader/partial-dispose` (an `isolate` edit on any row can move a realm; pi-ai's own also drops the cached host modules), which loader `1.0.7-alpha.2` and `1.1.0` emit for a removed row only after they deleted its entry and disposed its fiber, so a reconcile for a removed pi-ai row finds no live pi-ai and claims nothing rather than looking for the entry (`host-planes`' removed-row case).

- **Mount.** It runs inside apply's returned promise, never from a timer:
  1. Register the teardown effect first.
  2. Install the listener.
  3. If pi-ai holds a plane, `await piFiber.await()`; a FAILED pi-ai is tolerated. Restart pi-ai only if it is ACTIVE and its resolved config still holds a plane the claim takes, then check again.
  4. `registerAdapter` is wrapped in try/catch. On `DUPLICATE_ADAPTER` it logs and retries on the next `llm/adapters-updated`, after `piFiber.await()`.
- **Teardown.** A single effect, registered first so that it runs last:
  1. It calls the handle, then sets the listener inert, with no await between the two.
  2. Only on a real dispose (`ctx.fiber.uid === null`), with pi-ai ACTIVE and its parent not unloading, and only when it took a plane, it awaits pi-ai, restarts it so it takes the routes back, and checks the result through `listProviders()`.

  Reloading the plugin's own configuration restarts pi-ai zero times.

#### `src/host/plane-provider.ts`, `src/utils/plane-profile.ts` and `src/utils/plane-model.ts`

- **Where the classes come from.** `PiAiAdapter` and `Config` come from the host's llm-pi-ai module, through the existing `loadPiAiModule`. The host's pi comes through `loadHostPi`. Both lookups sit behind one function in `cordis-context.ts`, which the harness can replace. The registry and `adapter.config` are never read.
- **`class PlaneAdapter extends PiAiAdapter`.** It overrides `listModels`: when `super` answers `[]` or throws `MISSING_CREDENTIAL` (F18), it answers with the declared ids. Dispatch still fails loudly.
- **Auth (F19).**
  - **Credentials.** A credential store over `ctx.credentials`, keyed by the exported `recordKeyFor(route)` and using pi-ai's record mapping, so a host Sign-in record under `llm-pi-ai/opencode` keeps working.
  - **Environment.** `authContext.env(name)` reads the credentials service first, then the launch environment.
  - **Provider auth.** The composite provider's `auth` is pi's own `opencodeProvider().auth` / `opencodeGoProvider().auth`.
  - **Keys.** `resolveApiKey` follows D20.
- **`utils/plane-profile.ts` is pure and never throws.** It builds a `ResolvedPiAiProviderProfile` from a raw entry. Every field comes from the entry or the plugin's constants, and none is copied from a sibling profile. It sets:
  - `Config`'s defaults and every `PiAiProviderProfile` field;
  - `configuredMaxTokens`;
  - `retryPolicy`, through dsh-llm's `resolveRetryPolicy`;
  - `modelErrors` and `catalogError`, from a mirror of pi-ai's semantic checks minus "needs an api" (D15);
  - `piProvider`, built with `createProvider({ id, auth, api, models })`. `api` maps all four protocols, each wrapped in `withOpenCodeSessionHeader(<protocol>Api())`, from the host pi's public exports.
- **`utils/plane-model.ts` `planeModelFor` is pure.** Each field takes the first source that has it:

  | field | rule |
  | :-- | :-- |
  | protocol | catalog SDK (`PROTOCOL_FOR_SDK`, with `@ai-sdk/mistral` → completions as pi's own data has it) > the user's route-level `api` (only for ids the catalog does not classify) > `openai-completions` (D16, D26) |
  | name, context, max tokens, modalities, cost | the user's row > pi-ai's route-level `modelOverrides` > catalog > pi; past that pi-ai's own defaults, which the plugin does not restate (D17, D26) |
  | reasoning levels | the user's `reasoningEfforts` > `reasoningFor(spec)` from the catalog (D1: a toggle model offers Off/On, in both vocabularies) > pi > none |
  | baseUrl | the route-level `baseURL` > the `endpoint` family table |

  The baseUrl row resolves as follows:
  - A route-level `baseURL` on a vendor root (`/zen…`, `/inference…/openai/v1`, `/inference(/go)/v1`) selects that family.
  - A foreign root is used as written, except that a trailing `/v1` is stripped for anthropic-messages, because pi's Anthropic SDK appends `/v1/messages`.
  - The family table defaults to `modern`; `auto` means `modern`.
  - `legacy` takes the base from the fixed legacy table, never from pi's own entry (D26). Go has no legacy Google base, so that cell uses `OPENCODE_FAMILY_API.go["@ai-sdk/google"]`.

- **`src/utils/protocols.ts`**, created in P-R1, holds the SDK constants, `PROTOCOL_FOR_SDK` and `isServableSdk`. `UNSERVED_*` goes.

#### `src/host/patch-method.ts`: the two host wrappers that remain

`patch-method.ts` restores a wrapper only if it is still the current one, deletes it when the original was inherited, and re-wraps on `llm/adapters-updated`. It installs two wrappers:

- **`settings.describe` (D18, F20).** It runs inside `ctx.inject(["settings"])`, and touches only the `llm-pi-ai` descriptor. When `value.providers[plane]` is missing for a plane the claim takes, it sets it to the interpolated, `Config`-normalized committed entry (a stepped-aside plane, D27, is pi-ai's own and described by pi-ai); `base`, `user` and the revision are untouched. A contract test pins that no node under `providers` in pi-ai's `Config` carries `role("secret")`. Today only `apiKeyEnv` has a role, and it is `credential-ref`.
- **`discoverModels` (P3).** It answers pi's rows plus the catalog's missing ones, deduped and whitelisted. A `NO_DISCOVERY` while pi-ai restarts yields catalog-only rows. It complements only a plane the claim takes: a stepped-aside plane (D27) is answered by pi-ai alone, as the 1.x enrichment wrapper P3 replaces already does (it reads the claim's `steppedAside` per call).

## Target architecture

```
src/
  index.ts             apply, Config, inject, name + config types (D6)
  lifecycle.ts         apply(): installers only
  host/
    patch-method.ts    wrap a host method: restore only if still current; delete when the original
                       was inherited; re-wrap on llm/adapters-updated (settings.describe, discoverModels)
    discovery.ts       discoverModels: pi's answer + the catalog's missing models (D3, D8)
    route-claim.ts     internal/config filter (appended on the NEW core, F8): pi-ai never claims the planes; reconcile on
                       commit; mount and teardown ordering (F14-F17)
    plane-provider.ts  PlaneAdapter (extends the host's PiAiAdapter), registered as the declared planes
    remote.ts          installRemoteService, markRemote
  request/             fetch patch stages: claim → credential → headers → body (body parsed once)
  credentials.ts       gathers values; utils/credential-policy decides; CaptureStore per root
  utils/               pure: protocols, plane-model, plane-profile, model-metadata (reasoning, both
                       vocabularies), credential-policy, request-shape, session-id, catalog-parse
  contracts/           defineRemote(namespace, methods) for usage, purge, store (client-safe)
  settings-table.ts    one field table → schema, resolver, types, card specs, copy, manifest
  ui/                  card, one ActionRow, meter, on the primitives
```

The target removes the workaround's moving parts. There are no hidden routes, no listing hide, no stream redirect and no child mount. There is no Gemini bridge registration, no patched host adapter and no `resolveModelInfo` override (D8).

What stays private is pinned by contract tests against the real host packages:

- the `ResolvedPiAiProviderProfile` shape;
- pi-ai's credential record mapping;
- parity with pi-ai's own profile resolution;
- the two wrapped host methods, `describe` and `discoverModels`.

## Lessons from opencode2dsh

Two community plugins solve the same problem on the same host: [`FishBottle7/opencode2dsh`](https://github.com/FishBottle7/opencode2dsh) (read at `3805a38`, cited as FB) and [`satanfire/opencode2dsh`](https://github.com/satanfire/opencode2dsh) (read at `873e914`, cited as SF). Ranked by value. "Adopt" means the evidence is in the cited code; "measure" means P-R2 records it before any code moves.

| # | Lesson | Evidence | Phase | Verdict |
| :-- | :-- | :-- | :-- | :-- |
| L1 | **Shape plane traffic per call, not through the global fetch patch.** Put the derived session id, `x-opencode-client` and `x-opencode-project` into `options.headers`, and the core-tool fallback into `onPayload`, when wrapping each api in the plane provider; keep the fetch patch for URL-claimed relays, listing enrichment and P6's credential fill. Warn once when `globalThis.fetch` is no longer the patched function. | FB `packages/plugin/src/adapter/zen-adapter.ts` (`headers`, `onPayload`); FB `packages/plugin/src/pool/installer.ts` swaps `globalThis.fetch`, and our restore is identity-guarded. `docs/redirect-planes.md` claims the headers reach all four protocols; only the session header does. | P10a, P5 (the doc fix landed in P-R1, fa53d8e) | Adopt |
| L2 | **Classify the gateway's refusals as non-retryable in `prepareCall`**, keeping status and body. The host maps 403 to `AUTH` and 429 to `RATE_LIMIT`, and retries a 429 five times. | SF `lib/errors.js`; FB `packages/plugin/src/adapter/events.ts`. FB's claim that `AUTH` makes the UI print "API key is invalid" is unverified. | P-R3 | Adopt after verifying the UI claim |
| L3 | **The free probe misreads the newer refusal.** A final 429 is always read as rate-limited; `429 FreeUsageLimitError` is the gate refusing, so it is its own verdict and is not retried. Also probe the root family `/inference/v1`. | SF `873e914` (the probe no longer counts a 429 as usable); FB `packages/plugin/src/adapter/catalog.ts` counts a 429 as a pass. | P-R2 | Adopt |
| L4 | **Measure `x-opencode-request` before keeping it.** We send a minted `msg_` id, and the keyed probes omit it, so it has never been measured. | FB `packages/plugin/src/adapter/ids.ts` ("any value is refused"); SF removed it; `docs/upstream-findings.md` says 2.x dropped it. | P-R2 rows, then P6 or P10a | Measure; drop it or send it only where accepted |
| L5 | **`x-opencode-project` has three conflicting claims:** the folder basename (ours, which also leaks the repository's name), `global` (FB), and a 40-hex digest (SF). | FB `packages/plugin/src/adapter/ids.ts`; SF `lib/protocol.js`. | P-R2 rows for all three, then default to `global` unless another is proven | Measure; probably change the default |

## End-to-end infrastructure

### The `e2e-host` job (`ci.yml`)

**When it runs:** on dispatch, nightly, and on PRs that touch the host seam — `src/host/**` and, beside it, `src/lifecycle.ts`, `src/identity.ts`, `src/cordis-context.ts` and `src/models-discovery.ts`, whose behaviour depends on the real loader and apply order, and the two modules that still install host-level patches until P6/P10a move them under `src/host/` (`src/fetch-patch.ts`, the global fetch wrapper whose order the probe reads, and `src/stream-hook.ts`) (every other row producer, such as the pure plane model and profile in `src/utils/`, `src/key-capture.ts`, `src/models-catalog.ts` or `src/config.ts`, is covered on each PR by the in-process characterization of the same rows, and by the nightly run) — `cordis.patch.yml`, `test/e2e/host/**`, `test/e2e/host-binary.e2e.ts`, `test/support/host.ts`, `test/support/host-versions.ts`, `scripts/host-drift.ts` (the family table the binary e2e asserts against the installed manifests), `.github/workflows/ci.yml`, `vitest.e2e.config.ts` or `vite.config.ts` (the pack config that builds `lib/index.mjs`, which only this job loads into a real host, and the test settings the e2e config inherits) (scoped by a step, since a workflow-level path filter would silence every job).

**What it does:**

1. Installs each channel's `@deepseek-ai/dsh` (its record's `dsh`) into a throwaway prefix with npm, pi unpatched: the npm cell is exactly what npm resolves and is never cached (re-resolving is its point); the floor cell is the tree the desktop app ships, forced with npm `overrides` (`floorOverrides`: the channel's cordis family at the record's versions, the declared ranges' floors, and pi with its telemetry package at the range's floor), and is cached by channel, `dsh` and a hash of those overrides; the rest of its tree is what npm resolved when the cache was filled. In both cells the e2e holds each cordis-family field to the floor of the range the installed published package declares, with one rule for cosmokit: its declarer is cordis, so it is checked only where the installed cordis is the record's, and elsewhere only the nightly drift report checks it (measured 2026-11-12, every cell's installed cordis is its record's, so cosmokit is checked in all four).
2. Asserts the installed `dsh` is the channel's, one pi copy, and the pi that resolved: on the floor cell, pi and every cordis family member exactly; in the npm cell, pi inside the bridge's range, and the record's newest for the pi-dependent rows to run (a newer pi skips them with a warning).
3. Builds, and boots a temporary HOME whose profile links the checkout through a relative `link:`.
4. Runs `test/e2e/host/probe-plugin.mjs` together with `test/e2e/host-binary.e2e.ts`, which runs only when `DSH_HOST_E2E=1`.

**Cells:**

- (a) each channel's published binary, with pi as npm resolves it (D14''), on PRs that touch the host seam, nightly and on dispatch; it asserts the `newest` cell's rows;
- (b) each channel's floor pi, nightly and on dispatch; it asserts that channel's floor cell's rows.

Since P-R1 every cell is one row table, and an npm cell whose pi moved past its channel record skips only the per-model rows (a newer pi's own entry can still move a model's metadata where the catalog states none); the listings before and after a turn, the save rows and the row that the plane provider is built from the host prefix's own pi are asserted in every cell, since none of them depends on which ids pi describes, and the route claim engages on both host cores. Its probe JSON is the record.

Only the npm cell lets cordis float, as the published host's `~` ranges do for a user. A host that cannot run its own save path under what npm resolved is a `[HOST_LIMITATION]` row, detected from the host's answer and never from a version: the plane edit and a control edit no plugin's listener reads (the probe's own entry) both fail with the same `TypeError` thrown by `@deepseek-ai/dsh-app-boot`; the save rows then skip (D26), and where the host saves, the row skips and a `[BASELINE]` row asserts the control was accepted. Measured 2026-11-03: alpha `0.2.2-alpha.2` as npm installed it resolved cordis `4.0.6-alpha.2`, whose new `internal/update` call shape broke `dsh-app-boot`'s own listener, so no config-editor save succeeded on that alpha npm cell. Re-measured 2026-11-12 on the records' builds, `0.2.2-alpha.3` and `0.2.2-rc.2`: all four cells (`npm` and `floor` per channel) save the control edit, the detector row skips, and the save rows run and pass.

The NEW core both records run (cordis `4.0.6-alpha.2`, `4.1.0`) hands `internal/config` listeners the fiber and reads the config from `next()`; the OLD one (cordis `4.0.5`, `4.0.6-alpha.1`) binds the fiber as `this` and passes the config. The route claim speaks both (P-R1), and the probe records the shape of every dispatch it sees (`configHook`, the first; `configHooks`, a count per shape), read with the claim's own fiber predicate, never from a version. A `[BASELINE]` row requires one known shape throughout and both planes on the plugin's `PlaneAdapter`; it was a `[KNOWN_DEFECT]` row asserting that pi-ai served both planes, with the plane-provider, registry, listing, per-model, Gemini-level, Settings-graft and save rows skipping by name, until the claim spoke the NEW shape.

### The live gateway job (`OPENCODE_API_KEY` / `OPENCODE_GO_API_KEY`)

What spends a key is a tier, `OPENCODE_E2E_KEYED`, which a step of the `e2e` job sets per event; the keys are passed only when it is not `none`:

| Run | Tier | What runs |
| :-- | :-- | :-- |
| a PR | `none` | the keyless cases only, no key spent: the matrix, the free probe, the System One family's three shapes (recorded), and the keyless cases of protocol-routing and opencode-live |
| a PR touching `src/host/**`, `src/utils/protocols.ts`, `src/utils/plane-model.ts`, `src/identity.ts`, `src/utils/request-shape.ts` or the probes' own inputs | `probes` | adds the keyed probes: one request of a few tokens per plane × protocol × URL shape, plus six recorded variants of each plane's default completions cell (request id, project, reasoning effort) and every 429's `Retry-After` |
| nightly, dispatch | `full` | adds the full keyed suites |
| a push to main | `none` | keyless only |

- **The keyless matrix** (every run): 3 shapes × 4 protocols × 2 planes. A 404 means the path is gone; a 400 "Model is unavailable", a 410 or a refusal of type `ModelDeprecated` at any status means the model is gone. It asserts that every cell has a model and was sent, that every legacy and modern answer is readable (a redirect, a rate limit or no answer is not), and that no cell the default dispatches to (`TODAY_DISPATCH`: all four protocols on the modern family, on every host cell) answers 404. The free probe asserts that a free completions model is served or free-tier-gated on `/inference/openai/v1/chat/completions`; a retired model (a `ModelDeprecated` refusal included) or a busy upstream moves on to the next candidate (`runFreeProbe`, which records the deciding candidate's own model and status), and it skips on a rate limit, a busy upstream no candidate got past, or the free tier's usage cap (`429 FreeUsageLimitError`, `free-usage-limited`), never retried and never read as served.
- **The keyed probes** (`probes` and `full`), per plane, from the `TODAY_DISPATCH` cells, each read beside the legacy and root cells of the same protocol (same model, same key): it fails when one answers path-gone, wrong-protocol or auth-refused, a retired model another shape accepted, or nothing readable — `other`, a redirect, a refused session, `transport-error` or `no-model`. Flip evidence is a wrong-protocol, path-gone, auth-refused or model-gone on the modern cell while the cell `endpoint: legacy` dispatches to — a different one — accepted the request (an unreadable answer never is); a refusal only the root or Go Google's `/zen/go` cell accepted is red but not evidence, a key refused on every shape that read it names the CI secret instead, and a protocol or a path the flip's cell measured nothing about asks for a re-run. It skips when none of them was served (the account's answer, a rate limit, a busy upstream, a retired model, a parsed but refused body), since that measured nothing.
- `endpoint: legacy`'s cells (completions, Responses and Messages on both planes, and Zen's Google) and the root shape are recorded, not asserted on their own — a legacy keyless answer must still be readable, but its path-gone fails nothing; Go's Google stays on `/inference/go/google/v1beta` under every family (`GO_GOOGLE_BASE_URL`), a default cell guarded as one.
- Both probe suites write a dated table to the run summary and the `endpoint-families` artifact; a run's tables are pasted into `docs/redirect-planes.md` §13.

## How each phase is built

1. **A spec**, written from this document and the code. It names the files, the first tests and their exact assertions, and the verification commands.
2. **The implementation.** The first test goes red on the base, or green for a pin. Then the change is made, and the gate below runs.
3. **A review panel**, running three reviews in parallel:
   - correctness and the host's contracts;
   - whether the tests perform the behaviour, plus coverage;
   - the repository's rules, the docs and this plan.

   Two independent skeptics check each finding. Fixes repeat until no blocker or high finding survives.

4. **The PR.**
   - It is stacked on the previous phase, under a Conventional title.
   - It names the rows it flips, and ticks its status row here.
   - CI failures are fixed on that branch; the phases above it are then rebased onto it, each as its own change.
